# md-sync

# 

If you write a Markdown source file in * * Chinese or English * *, md-sync will * * automatically translate it into another language * * and generate it at the same time
Output in multiple formats (HTML/PDF/Markdown, etc.); all products are automatically regenerated once the source file is changed. Efficiency artifacts for document workers.
- One source → multiple products: `html/zh`, `html/en`, `pdf/zh`, `pdf/en`, `md/zh`, `md/en`, …
- → Automatic resynchronization of source files changed (with anti-shake/debounce)
- Translation away * * cache first * *: the existing translation is directly reused, and the deletion is only reverted back to AI
- Comes with web-style UI and native desktop GUI

## Why is md-sync needed?

Give "repetitive, tedious, error-prone physical work" to md-sync and you focus on the content itself. AI tools do translate documents and convert formats - but that solves a “one-time” need.
What is really cumbersome is the scenario of * * frequent modification of the source file * *: every time you change a word, you have to go through it manually.
* * Modify → → translation formats * * is the whole link, and it is often necessary to maintain products in multiple languages and formats at the same time.
Manual repetitive operation is not only time-consuming, but also easier to overturn, overturn, and uneven versions.
* * md-sync was born for this scenario: you just change the source file and leave the rest to the tool. * *
- * * What's changed is what you get * *: Based on file monitoring, once the source file is saved, the products in all languages/formats are automatically regenerated within seconds.
- * * One-time configuration, long-term benefits * *: Translation cache + multiple output configuration only needs to be set once, and there are zero additional operations per subsequent modification.
- * * Not prone to errors * *: Translations and formats are handled uniformly by the tool to avoid missing translations, omissions, and mistakes caused by manual copy and paste.

## Use processes

md-sync is only responsible for "turning the manuscript into a publication", * * the manuscript is still written using your best Markdown editor * *:
1. * * Write in your favorite MD editor * *: For example, [Typora] (https://typora.io/), Obsidian, VS Code, etc., write the `.md` source file according to your habits.
2. * * Give to md-sync to automatically generate and publish documents * *: Give the source file to md-sync, it will automatically synchronize the products in multiple formats (HTML/PDF/Markdown/DOCX/EPUB) and multiple languages (Chinese/English) as configured, and automatically regenerate when the source file changes.
3. * * Use Typora themes to produce beautiful documents * *: md-sync can directly use the rich theme resources (such as bloom-mist, night, claude-like, etc.) under the Typora theme directory on your computer to render HTML/PDF documents in a unified style, without having to rewrite them yourself. * * Provided you have [Typora] (https://typora.io/) installed natively * * - the theme CSS is stored in Typora's configuration directory, otherwise it will not appear in the Render Style drop-down box.
> In a nutshell: * * You just write it in the editor, and md-sync is responsible for turning it into a nice-looking release. * *

## Why write with Markdown (instead of docx)

The core value of a document workflow is “comparable, traceable, and collaborative”, and the file format directly determines whether you can do this with a mature toolchain:
- * * Markdown is plain text * *: basically no binary formatting control, essentially an enhanced version of `.txt`. So it naturally connects to text workflows that programmers have already validated:
- * * Comparison of differences * *: use `diff` or any code comparison tool to directly see the addition, deletion and modification, and compare line by line at a glance;
- * * Version management * *: Manage documents with version control systems such as` git `- submit history, branch, rollback, multiplayer collaboration merge are all available;
- * * Automation * *: Text can be parsed by scripts, processed in batches, and automatically checked and published by CI.
- * * docx/pdf/epub, etc. are in binary format * *: the content is packed into a proprietary container, the ordinary text tool can not read the differences, can not do `diff`, and it is difficult to make meaningful version comparisons in git (each time the entire file changes, the history is bloated and unreadable).
> Conclusion: * * Markdown is only used as a "source format" for editing and collaboration, and binary formats such as docx/pdf/epub should only be used as an "output format" * * --automatically generated by md-sync from the same Markdown source, and should not be used in turn as an editing format. In this way, you can enjoy the publishing compatibility of binary format while retaining the difference comparison and version management capabilities of plain text.

## Feature Overview

| Ability | Description |
|------|------|
| * * Multi-format output * * | `html` `md` `pdf` with plugin extension `docx`/`epub` (PDF generated by Chromium) |
| * * Multilingual output * * | `en`/`en`, translation based on `.translations.json` cache, missing fallback AI (provider `auto`) |
| * * File Snooping * * | Based on `watchdog` snooping source files, `debounce` defaults to 1.5s, change and sync |
| * * Templates/themes * * | Built-in styles such as` bwx `,` modern `, etc.; and directly select themes under the Typora theme directory (` ~/.config/Typora/themes/`) (` typora-bloom-mist `,` typora-night `,` typora-claude-like `, etc.), automatically compatible with backgrounds, dark/light and code blocks (` md-sync template `/` md-sync plugin `) |
| * * Translation cache * * | `strategy: mapping` + `mapping_file`, translations only update the cache dictionary, do not directly exit the file, access it when rendering |
| * * Web Dashboard * * | Configure source files in your browser, view parsing information, start/stop listening, sync manually, view sync events and history items |
| * * Desktop GUI (Qt native) * * | PySide6 native interface, calling the core pipeline directly, continuously listening for synchronization, zero HTTP servers |
| * * Standard document (gongwen) * * | Built-in document plugin: Write Markdown by template and export redhead document `docx`/'pdf` (redhead, layout, page number automatic typography) in accordance with GB/T 9704-2012 with one click |

### Typora theme compatible with PDF export

md-sync will automatically discover the topics in the native Typora theme directory and
Format selection of 'typora-` (e.g. `typora-bloom-mist`/`typora-bloom-mist-dark`/
`typora-night`/`typora-claude-like`, etc.). * * Requires Typora to be installed on the machine * *; the subject directory for different systems is:
- * * Windows * *: `% APPDATA %\ Typora\ themes`
- * * macOS * *: `~/Library/Application Support/abnerworks.Typora/themes`
- * * Linux * *: `~/.config/Typora/themes`
<https://github.com/zagwi/typora-themes-util> Access all community themes recommended by Typora's website that can be downloaded and installed at once.
When the above directory is not detected, the Typora theme will not appear in the "Render Style" drop-down box, and the GUI will prompt "No Typora installed on this machine is detected".
Render layer for Typora Editor Theme vs.
The differences in "single file HTML/PDF" are compatible to ensure that these themes can also be correctly rendered under md-sync:
- * * Background and card appearance * *: Typora themes often rely on a "dark shell + white card (`# write`)" double layer structure;
And md-sync only generates`<body><div id="write"> `Single layer, so the background color is derived from the` --bg `variable of the theme
The card has a solid color base and is universal with light/dark.
- * * Title/body color * *: use variable fallback chain (`--text`/`--text-color'), legacy theme
(such as night) will not be mistakenly washed into a light color, nor will the dark theme be output as light.
- * * Code block * *: The `pre` rule of the Typora theme qualifies the `.md-fences` class, whereas the md-sync output is
`<pre class="language-*">`, so complement the generic code block style and be compatible with bloom (`--code-bg`),
night (`--bg-color`), claude (`--code-bg-color`), and more.
The PDF export (Chromium engine) has been optimized for a "professional look":
- Force `print-color-adjust: exact`, keep the theme background color for the whole page (no longer whitening the whole page);
- Suppresses header footer (date/URL/page number) and is compatible with `--no-pdf-header-footer`
`--no-print-header-footer` two-parameter writing (one for each Chromium version/distribution);
- `@ page {margin: 0}` with `padding` for `# write`
(`box-sizing: border-box` + `box-decoration-break: clone`) to make each page
The margins (including the last page) are consistent and have no glaring white borders.

## Gongwen Plugin: Standard Gongwen Export

`gongwen` is a built-in * * standard doc plugin * * for md-sync: just press the template to write a copy of Markdown and export with one click * * fully compliant
GB/T 9704-2012 "Official Document Format of Party and Government Organs" * * Official Documents` docx `and` pdf `—— Redhead, layout, payment, page number are all automatically typed without manual set.
* * One source manuscript → standard document * *:
source: Notification.md
schema: gongwen # Enable doc plugin
outputs:
  - format: docx # standard official docx
    lang: zh
    path: out/Notification.docx
  -format: html
    lang: zh
    style: gongwen # Document rendering style (independent of Typora)
    pdf: true
    pdf_path: out/Notifications.pdf # Standard Document pdf
* * Source manuscript format * *: Fill in the blank according to the template, and each position segment (issuing authority logo/issuing text number/sending authority/title/
body/attachment/signature/date of writing/note/notation) corresponds to one of the following official formats:
md-sync plugin template gongwen -o notification .md # Generate source document template
**字体**：Windows 一般自带国标字体；Linux 缺失时 GUI 会提示一键下载免费 Fandol 字体集。

pip install PySide6

## 安装

要求 **Python ≥ 3.10**，并装有 `pip`。在仓库根目录（含 `pyproject.toml`）执行：
pip install -e .
依赖：`pyyaml`、`jinja2`、`watchdog`、`fastapi`、`uvicorn[standard]`、`httpx`。
桌面 GUI（Qt）额外需要 PySide6：
pip install PySide6

### 系统级前置依赖：Chromium（仅 PDF 导出需要）

PDF 由本机 **Chromium / Chrome** 以 headless 方式打印生成，**它是系统级前置依赖，`pip install` 不会自动下载**。导出 PDF 前请确保本机已安装，且 `md-sync` 能找到其二进制：
- **Arch / Manjaro**：`sudo pacman -S chromium`
- **Debian / Ubuntu 等**：`sudo apt install chromium`（或安装 Google Chrome）
- **macOS**：`brew install --cask chromium`（或安装 Google Chrome）
- **Windows**：从 [chromium.org](https://www.chromium.org/) 或 Google Chrome 官网安装
安装后 `md-sync` 会自动探测 `/usr/bin/chromium`、`google-chrome*`、`/snap/bin/chromium` 等常见路径；若装在非常规位置，可在配置中通过 `chromium_path` 显式指定二进制路径。未安装或探测不到时会直接报错中止，不会静默降级。

## 制作插件

md-sync 的插件分两类目录：**`md_sync/plugin/`** 是插件**引擎代码**（接口 / 注册表 / 加载器 / 钩子），**`plugins/`** 与 `~/.md-sync/plugins/`** 才是插件**实例**（具体模板、解析器）。你只需按约定放一个目录，无需改引擎代码即可扩展渲染风格、解析器或钩子。
完整可运行示例见 **`docs/example-plugin/`**（`resume-pack`：源模板 + 解析器 + 渲染风格 + 过滤器四件套）。

### 插件目录结构

my-plugin/
├── plugin.yaml          # 插件清单（必填）
├── template.md          # 源模板（仅 pack 类型需要；用户按此格式写稿）
├── parser.py            # 解析器（仅 pack/parser 类型需要）
├── templates/           # 渲染风格（Jinja2 + CSS）
│   └── <style-name>/    #   一个子目录 = 一种风格，目录名即风格名
│       ├── document.html.j2
│       └── style.css
└── filters.py           # 可选：自定义 Jinja2 过滤器

### plugin.yaml 清单字段

name: resume-pack            # 唯一标识，用于 md-sync plugin remove <name>
version: "1.0"
description: 一句话描述
author: Your Name
type: pack                  # render | parser | pack | translate | export | hook
# type=pack 时：解析器 + 源模板 + 渲染风格打包在一起

parser:                     # 仅 pack/parser 需要
  class: parser.MyResumeParser   # parser.py 里的类名
  schema: my-resume              # 配置里 schema: my-resume 引用此插件

template: template.md       # 源模板相对路径（pack 类型）

templates:                  # 本插件提供的渲染风格名（须与 templates/<name>/ 目录一致）
  - example-style

hooks:                      # 监听的流水线钩子
  - after_parse
  - after_render

dependencies: []
> ⚠️ **`templates:` 里写的风格名必须真实存在于 `templates/<name>/` 目录**，否则该风格不会出现在 `md-sync template list` 中（也不会报错，只是不生效）。

### 三种常见插件类型

| 类型 | `type` | 用途 | 关键文件 |
|------|--------|------|----------|
| 渲染风格 | `render` | 只提供新 HTML/CSS 样式 | `templates/<style>/` |
| 自定义解析器 | `parser` | 让 md-sync 读懂特殊格式源稿 | `parser.py` |
| 完整插件包 | `pack` | 源模板 + 解析器 + 风格一体 | 上述全部 |

### 写解析器（pack/parser 类型）

继承 `md_sync.plugin.interface.ParserPlugin`，实现 `_parse` 把源文本转成 `Document` 模型：
from md_sync.plugin.interface import ParserPlugin, PluginManifest, PLUGIN_TYPE_PACK
from md_sync.core.document import Document, Item, Section

class MyResumeParser(ParserPlugin):
    def __init__(self):
        self._manifest = PluginManifest(
            name="resume-pack",
            plugin_type=PLUGIN_TYPE_PACK,
            parser_schema="my-resume",   # 配置 schema 引用
        )

    @property
    def manifest(self) -> PluginManifest:
        return self._manifest

    def detect(self, text: str) -> bool:
        """自动识别该源是否属于本插件格式（返回 True 时被自动选用）。"""
        return "## 工作经历" in text and "---" in text

    def parse(self, text: str) -> Document:
        doc = Document()
        # ... 按自己的语法把 text 解析成 doc.sections / doc.items ...
        return doc
解析出的 `Document` 会交给模板渲染；`detect()` 命中后，配置里写 `schema: my-resume` 即可指定使用它。

### 写渲染风格（render/pack 类型）

在 `templates/<style-name>/` 下放 Jinja2 模板与 CSS。`Document` 模型的字段（`doc.name`、`doc.sections`、`doc.items` 等）即为模板可用变量。需要自定义过滤器时，在 `filters.py` 暴露一个 `filters` 字典：
def highlight_metric(text: str) -> str:
    return text  # 实际实现略

filters = {            # DirectoryPlugin 自动发现并注册
    "highlight_metric": highlight_metric,
}
模板里即可使用 `{{ value | highlight_metric }}`。

## 配置文件（md-sync.yaml）

project: my-project                 # 项目名（仅内部标识）
source: README.md                   # 源 Markdown 路径
schema: resume                      # 解析模式（如 resume）

output_root: ./output               # 输出根目录（可省略，写在各 path 里也行）

outputs:
  - format: html                    # html / md
    lang: zh                        # zh / en
    pdf: true                       # 是否导出 PDF（需 Chromium）
    pdf_path: output/zh.pdf
    style: bwx                      # 模板/主题名
    page_size: A4                   # 页面尺寸：A4 / A3 / A5 / Letter / Legal（PDF、DOCX 通用）
    page_margin: ""                 # 留空 = 该尺寸的标准边距（A4→15mm、Letter→25.4mm…）；
                                    # 也可显式指定，如 "15mm" 或 "5mm 8mm"（上/下 左/右）
  - format: md
    lang: en
  - format: html
    lang: en
    pdf: true
    style: bwx

watch:
  enabled: true
  debounce: 1.5                     # 防抖秒数

translation:
  strategy: mapping                 # 缓存优先
  mapping_file: .translations.json  # 译文缓存文件
  ai:
    provider: auto                  # 缺失译文回退的 AI provider

web_ui:
  enabled: true
  host: 127.0.0.1
  port: 8580
要点：
- `source` 指向你的源 Markdown。
- `outputs` 每项是一个「格式 × 语言」组合；`html` 可指定 `style` 并可选 `pdf`。
- `translation.mapping_file` 是译文缓存：翻译只更新该 JSON，渲染时再取用，因此**翻译本身不直接生成输出文件**。

### 2. 单文件可执行程序（PyInstaller，推荐）

仓库自带跨平台构建脚本 `scripts/build_app.py`，在当前系统上产出免 Python 环境的可执行文件：
pip install pyinstaller            # 或 pip install -e ".[build]"
python scripts/build_app.py                # 产出 dist/md-sync (Linux/macOS) 或 dist/md-sync.exe (Windows)
python scripts/build_app.py --clean        # 清缓存后重新构建
**产物位置（均在本项目 `dist/` 目录下）：**
| 平台 | 产物路径 | 说明 |
|------|----------|------|
| Linux   | `dist/md-sync`        | ELF 可执行文件，直接 `./dist/md-sync --help` 运行 |
| macOS   | `dist/md-sync`        | 同 Linux 命名，需在 macOS 上构建 |
| Windows | `dist/md-sync.exe`    | 需在 Windows 上构建 |
> 当前环境是 Linux，本地构建只会得到 `dist/md-sync`；Windows / macOS 二进制需在对应系统
> 或下面的 CI 上产出。`dist/`、`build/`、`*.spec` 都已写入 `.gitignore`，不会进版本库。
- 脚本自动把 `md_sync/templates`、`md_sync/themes`、`md_sync/web` 等资源打进 bundle，
运行时通过 `md_sync.template.manager._find_install_dir()` 解析，**无需用户机器安装任何东西**。
- **构建 Python 版本建议用 3.12**（PyInstaller 官方稳定支持）。在 3.14 上需排除 `mypy`
（脚本已默认 `--exclude-module mypy`，因其 mypyc 扩展与 3.14 的 CArchive 压缩不兼容会导致
exe 启动即崩溃 `decompression resulted in return code -3`）。

### 3. 跨平台自动构建（GitHub Actions）

`.github/workflows/build.yml` 在 `ubuntu-latest` / `windows-latest` / `macos-latest`
三个 runner 上分别运行 `python scripts/build_app.py`，将三个平台的可执行文件作为 Release artifact 上传。
# 打 tag 触发自动构建并发布 Release
git tag v1.0.0 && git push origin v1.0.0
# 到 GitHub Releases 页面下载：md-sync-linux / md-sync-windows.exe / md-sync-macos
若只想临时取三平台二进制（不发 Release），在 Actions 对应 run 的 Artifacts 里下载即可，
artifact 命名为 `md-sync-ubuntu-latest` / `md-sync-windows-latest` / `md-sync-macos-latest`。

## 常见问题

- **「打开」选完文件后输入框清空**：这是预期行为——选文件即加载，无需手填路径。
- **翻译后为什么还有 HTML？** 翻译只换文字（语言），HTML 由渲染器（转换）生成（格式），两者是各自独立的产物，可分别勾选。
- **Qt GUI 的同步日志在哪？** 直接显示在 GUI 的「同步日志」面板中。
- **端口被占用？** Web 模式默认使用 8580；若该端口被占用，改 `web_ui.port` 即可。
