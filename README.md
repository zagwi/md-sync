# md-sync

Write a Markdown source file in **Chinese or English** and md-sync will **automatically translate it into the other language** while generating multiple formats (HTML / PDF / Markdown / DOCX / EPUB) at the same time. Any change to the source regenerates every artifact automatically — a productivity boost for anyone who works with documents.

- One source → many artifacts: `zh` / `en` × HTML / PDF / Markdown / DOCX / EPUB — write once, ship everywhere
- Auto-regeneration on save — no manual steps
- **Cache-first translation**: existing translations are reused, only missing pieces fall back to AI, so text is never re-translated needlessly
- Three entry points of your choice: **desktop GUI, web dashboard, CLI**

## For the curious

### Why do you need md-sync?

Hand the "repetitive, tedious, error-prone grunt work" to md-sync so you can focus on the content itself. AI tools can translate documents and convert formats — but they only solve the **one-off** case. What is genuinely tedious is **frequently editing the source**: every time you change a word, you must manually walk the whole **edit → translate → convert** chain, often while maintaining several languages and formats at once. Repeating that by hand is not just slow — it invites missed translations, missed conversions, and divergent versions.

**md-sync exists for exactly that scenario: you just edit the source; it handles the rest.**

- **What you edit is what you get**: save the source and every language / format artifact is regenerated within seconds.
- **Configure once, benefit forever**: the translation cache and multi-output settings are set up a single time; every later edit needs zero extra steps.
- **Fewer mistakes**: translations and formatting are handled consistently by the tool, avoiding the leaks, misses, and broken layouts of copy-paste.

### Feature overview

| Capability | Description |
|------|------|
| **Multi-format output** | HTML / PDF / Markdown / DOCX / EPUB, in any combination |
| **Multi-language output** | Automatic zh / en translation, cache-first with AI fallback for missing pieces |
| **Auto-regeneration** | Saving the source updates every selected format / language artifact automatically |
| **Render themes** | Several built-in themes, plus direct reuse of your local [Typora](https://typora.io/) themes |
| **Desktop GUI** | Native window: pick the source, tick formats, done |
| **Web dashboard** | No config file needed — upload a source, watch the log, download artifacts in the browser |
| **Official documents** | Built-in template for exporting GB/T 9704-2012 compliant `docx` / `pdf` official documents |

### Why write in Markdown (instead of docx)

A document workflow is only as valuable as it is **comparable, traceable, and collaborative** — and that power is decided by the **source format**:

- **Markdown is plain text**: essentially an enhanced `.txt`, so it plugs straight into mature text workflows — line-by-line `diff`, `git` versioning (history, branches, rollback, collaboration), and scriptable batch processing and linting.
- **docx / pdf / epub are binary formats**: content is packed inside proprietary containers; ordinary text tools cannot surface meaningful differences, so meaningful diffs are impossible and histories keep bloating into unreadable messes.

> Conclusion: **Markdown stays the "source format" for editing and collaboration; docx / pdf / epub are "output formats"** — generated by md-sync from that single source. You get the publishing compatibility of binary formats without losing the diff and versioning power of plain text.

### How it works

A single source file flows through: **parse → translate (cache-first, AI fallback for missing pieces) → typography normalization → render → export**.
If you are curious about the implementation (data pipeline, plugin mechanism, packaging), jump to the **[Developer guide](#developer-guide)**.

## For users

### Installation

Requires **Python ≥ 3.10** with `pip` available. In the repo root (where `pyproject.toml` lives):

```bash
pip install -e .
```

(Dependencies are installed automatically.) For the desktop GUI, additionally:

```bash
pip install -e ".[gui]"
```

#### PDF export: a local Chromium is required

PDFs are generated by a local **Chromium / Chrome**, which **`pip install` will not download for you**. Before exporting PDFs, make sure one is installed:

- **Arch / Manjaro**: `sudo pacman -S chromium`
- **Debian / Ubuntu etc.**: `sudo apt install chromium` (or install Google Chrome)
- **macOS**: `brew install --cask chromium` (or install Google Chrome)
- **Windows**: install from [chromium.org](https://www.chromium.org/) or the Google Chrome website

md-sync auto-detects common paths (e.g. `/usr/bin/chromium`) after installation; if the binary lives somewhere unusual, point to it explicitly with `chromium_path` in the config.

### Usage

> The desktop GUI, web dashboard, and CLI all share the same sync engine — pick whichever fits the moment.

#### Option A: standalone desktop app (Dioxus, no Python needed)

A native window (Dioxus) talking to the same sync engine **bundled inside** — the deliverable is a single executable you can copy anywhere and run, **no Python required on the target machine**.

```bash
python scripts/build_desktop.py   # one command → dist/md-sync-ui (embedded backend, no Python needed)
./dist/md-sync-ui                 # run — the embedded backend auto-starts on :8580
```

The app talks to the backend over a **local Unix socket** (no HTTP, no network port). At startup it: ① reuses an already-running backend on the IPC socket; ② otherwise looks for a bundled backend next to the executable (or in the repo `dist/`, or extracts the embedded copy to the cache dir) and runs `md-sync ipc`; ③ only if none is found does it fall back to `python -m md_sync.web.ipc` (development only).

#### Option B: web dashboard

A browser-based interface that needs no config file: upload the source, set the output directory / formats / languages, toggle typography rules, watch the sync log live, and download artifacts — all in the page.

```bash
md-sync start                  # opens http://127.0.0.1:8580
python -m uvicorn md_sync.web.app:app --host 127.0.0.1 --port 8580   # equivalent, no entry point needed
```

#### Option C: CLI

```bash
md-sync init                  # writes a default md-sync.yaml in the current directory
md-sync sync -c md-sync.yaml          # one-shot sync
md-sync status -c md-sync.yaml        # show parsed config and output status
md-sync dry-run -c md-sync.yaml       # preview what would change (writes nothing)
md-sync template list                 # list available templates
md-sync plugin list                   # list installed plugins
```

### Using Typora themes

md-sync auto-discovers locally installed Typora themes and exposes them as `typora-<theme-name>` (e.g. `typora-bloom-mist`, `typora-night`, `typora-claude-like`). **Typora must be installed on this machine**; theme directories are:

- **Windows**: `%APPDATA%\Typora\themes`
- **macOS**: `~/Library/Application Support/abnerworks.Typora/themes`
- **Linux**: `~/.config/Typora/themes`

Visit <https://github.com/zagwi/typora-themes-util> to install Typora's recommended community themes in one go.
When no such directory is detected, Typora themes do not appear in the "render theme" dropdown (the UI shows "Typora not detected on this machine").

### The gongwen plugin: standard official documents

Write a Markdown source from the template, and md-sync exports a **GB/T 9704-2012《Party and government official document format》**-compliant `docx` and `pdf` in one go — red masthead, layout, signature block, and page numbers are all typeset automatically:

```yaml
source: 通知.md
schema: gongwen                     # enables the official-document plugin
outputs:
  - format: docx                    # standard official-document docx
    lang: zh
    path: out/通知.docx
  - format: html
    lang: zh
    style: gongwen                  # official-document render theme
    pdf: true
    pdf_path: out/通知.pdf          # standard official-document pdf
```

Fill in the template (issuing authority heading / document number / addressee / title / body / attachments / signature / date / notes / edition marks):

```bash
md-sync plugin template gongwen -o 通知.md    # generate the official-document source template
```

**Fonts**: Windows generally ships the required national-standard fonts; on Linux, if fonts are missing the UI offers to download the free Fandol font set.

### Configuration file (md-sync.yaml)

```yaml
project: my-project                 # project name (internal identifier)
source: README.md                   # source Markdown path
schema: resume                      # parse mode (e.g. resume; install plugins as needed)

output_root: ./output               # output root directory (optional)

outputs:
  - format: html                    # html / md / docx / epub
    lang: zh                        # zh / en
    pdf: true                       # also export PDF (requires Chromium)
    pdf_path: output/zh.pdf
    style: bwx                      # render theme name
    page_size: A4                   # A4 / A3 / A5 / Letter / Legal
    page_margin: ""                 # empty = standard margins; or e.g. "15mm" / "5mm 8mm"
  - format: html
    lang: en
    pdf: true
    style: bwx

watch:
  enabled: true
  debounce: 1.5                     # source debounce in seconds

translation:
  strategy: mapping                 # cache-first (AI fallback for missing pieces)
  mapping_file: .translations.json  # translation cache file

typography:                          # document typography rules (all enabled by default)
  enabled: true                      # master switch; off = artifacts identical to source
  cjk_latin_space: true              # space between CJK and Latin (支持ChatGPT → 支持 ChatGPT)
  cjk_digit_space: true              # space between CJK and digits (花100元 → 花 100 元)
  number_unit_space: true            # space between number and unit (20Gbps → 20 Gbps)
  fullwidth_punct_no_space: true     # no space beside full-width punctuation (iPhone ，好用 → iPhone，好用)
  en_no_space_before_punct: true     # no space before punctuation (Hello ,world → Hello,world)
  en_space_after_punct: true         # space after punctuation (Hello,world → Hello, world)
  en_collapse_spaces: true           # collapse repeated spaces (Hello   world → Hello world)
```

Notes:

- `source` points at your source Markdown; each `outputs` entry is one "format × language" combination, and `html` entries can specify a `style` and optionally export a `pdf` as well.
- Translation uses a **cache**: already-translated content is reused directly — no repeated translation calls, no re-generated files; only missing pieces fall back.
- `typography` rules apply **only to generated artifacts** (md / html / pdf) and **never modify your source**; code blocks, inline code, and URLs are always untouched. Use the "📐 Document standards" button in the UI (in-memory); from the CLI, edit this config section directly.

### FAQ

- **The input clears after picking a file with "Open"**: expected behavior — picking a file loads it, so there is no path to type.
- **Why is there still HTML after translating?** Translation changes the text (language); HTML is about the format (rendering). They are independent artifacts; tick them separately.
- **Where are the sync logs?** In the "Sync log" panel.
- **Do I need to restart after changing "Document standards" in the UI?** No — once saved, if watching is active, artifacts are regenerated immediately with the new rules; "Normalize source" also always uses the current config.

## Developer guide

For developers who want to extend md-sync, package it, or integrate it into their own projects.

### Project layout

```
md-sync/
├── md_sync/                # core package
│   ├── cli.py              # CLI entry points (md-sync sync / start / ipc …)
│   ├── config.py           # ProjectConfig parsing (md-sync.yaml)
│   ├── watcher.py          # file watching (watchdog + debounce)
│   ├── core/               # Document model + pipeline sync orchestration
│   ├── renderers/          # md / html renderers
│   ├── translate/          # translation management (mapping cache + AI fallback)
│   ├── exporters/          # PDF export (Chromium) / pandoc export (docx/epub)
│   ├── template/           # template management (incl. resource path resolution)
│   ├── web/                # web dashboard (FastAPI backend + static/index.html frontend)
│   └── plugin/             # plugin engine (interfaces / registry / loader / hooks), no plugin instances
├── plugins/                # built-in plugins (typora / resume / generic-markdown / gongwen), each ships its own templates
├── docs/example-plugin/    # plugin development example (resume-pack: source template + parser + render themes)
├── scripts/build_web.py    # package the Web edition (→ dist/md-sync-web)
├── scripts/build_desktop.py # package the desktop edition (→ dist/md-sync-ui)
├── tests/                  # test scripts
└── pyproject.toml
```

### Internals: the sync pipeline

```
Source file .md
   │
   ├─[1 Parse]     pick the parser from config.schema (plugin parsers win; default MdParser) → Document model
   ├─[2 Translate] look up .translations.json for each target language, reuse hits, fall back to AI on misses
   ├─[3 Typeset]   typography normalization (language-appropriate sub-rules; affects artifact text only)
   ├─[4 Render]    template rendering (Jinja2 + custom plugin filters)
   ├─[5 Export]    md / html written directly; pdf printed from html via Chromium; docx/epub via pandoc
   └─ save translation cache
```

Key points:

- **Translation cache** (`.translations.json`): translation only writes the cache file; rendering reads translations from it — so translation **never directly emits output files**, and repeated syncs rarely touch AI again.
- **Resource discovery**: after packaging, templates / plugins / web static assets resolve from inside the bundle via `md_sync.template.manager._find_install_dir()` — nothing needs to be installed on the user's machine.
- **Extensible docx export**: any plugin may register its own docx exporter (e.g. gongwen produces the red-masthead docx straight from internal data, with no pandoc involved); when none is provided, the pipeline falls back to the basic pandoc path.

### Writing plugins

md-sync plugins live in two kinds of directories: **`md_sync/plugin/`** is the plugin **engine** (interfaces / registry / loader / hooks), while **`plugins/`** and `~/.md-sync/plugins/`** hold the plugin **instances** (the actual templates and parsers). To extend render themes, parsers, or hooks, you just drop in a directory following the conventions — no engine code changes required.

A complete, runnable example lives in **`docs/example-plugin/`** (`resume-pack`: a teaching pack combining a source template + parser + filters).

#### Plugin directory structure

```text
my-plugin/
├── plugin.yaml          # plugin manifest (required)
├── template.md          # source template (pack type only; users write against this)
├── parser.py            # parser (pack/parser types only)
├── templates/           # render themes (Jinja2 + CSS)
│   └── <style-name>/    #   one subdirectory = one theme; the directory name is the theme name
│       ├── document.html.j2
│       └── style.css
└── filters.py           # optional: custom Jinja2 filters
```

#### plugin.yaml manifest fields

```yaml
name: resume-pack            # unique id, used by md-sync plugin remove <name>
version: "1.0"
description: one-line description
author: Your Name
type: pack                  # render | parser | pack | translate | export | hook
# type=pack bundles a parser + source template + render themes

parser:                     # pack/parser only
  class: parser.MyResumeParser   # class name inside parser.py
  schema: my-resume              # referenced from config as schema: my-resume

template: template.md       # relative path to the source template (pack type)

templates:                  # render theme names this plugin provides (must match templates/<name>/ dirs)
  - example-style

hooks:                      # pipeline hooks to listen to
  - after_parse
  - after_render

dependencies: []
```

> ⚠️ **Theme names listed under `templates:` must actually exist as `templates/<name>/` directories**; otherwise the theme won't show up in `md-sync template list` (no error, just no effect).

#### The three common plugin types

| Type | `type` | Purpose | Key files |
|------|--------|------|----------|
| Render theme | `render` | new HTML/CSS styling only | `templates/<style>/` |
| Custom parser | `parser` | teach md-sync to understand a special source format | `parser.py` |
| Full pack | `pack` | source template + parser + themes in one | all of the above |

#### Writing a parser (pack/parser types)

Subclass `md_sync.plugin.interface.ParserPlugin` and implement `_parse` to turn source text into a `Document` model:

```python
from md_sync.plugin.interface import ParserPlugin, PluginManifest, PLUGIN_TYPE_PACK
from md_sync.core.document import Document

class MyResumeParser(ParserPlugin):
    def __init__(self):
        self._manifest = PluginManifest(
            name="resume-pack",
            plugin_type=PLUGIN_TYPE_PACK,
            parser_schema="my-resume",   # referenced from config schema
        )

    @property
    def manifest(self) -> PluginManifest:
        return self._manifest

    def detect(self, text: str) -> bool:
        """Auto-recognize whether the source belongs to this plugin (picked automatically when True)."""
        return "## 工作经历" in text and "---" in text

    def parse(self, text: str) -> Document:
        doc = Document()
        # ... parse text into doc.sections / doc.items per your own grammar ...
        return doc
```

Once `detect()` matches, writing `schema: my-resume` in the config selects it.

#### Writing a render theme (render/pack types)

Put a Jinja2 template and CSS under `templates/<style-name>/`; the `Document` model fields (`doc.name`, `doc.sections`, `doc.items`, etc.) are the variables available to the template. To add custom filters, expose a `filters` dict in `filters.py`; `DirectoryPlugin` discovers and registers it automatically:

```python
def highlight_metric(text: str) -> str:
    return text  # real implementation omitted

filters = {"highlight_metric": highlight_metric}
```

Then use it in templates as `{{ value | highlight_metric }}`.

#### Installing and debugging

```bash
# install from a local directory (copies to ~/.md-sync/plugins/<name>/)
md-sync plugin install ./docs/example-plugin/resume-pack/

md-sync plugin list                              # list installed plugins and declared themes
md-sync plugin show resume-pack                  # show one plugin's manifest details
md-sync plugin template resume-pack -o my-resume.md   # generate the source template from the plugin
md-sync plugin remove resume-pack                # uninstall
```

Installing straight from a git repo or PyPI also works:

```bash
md-sync plugin install https://github.com/user/md-sync-plugin-xxx
md-sync plugin install some-pypi-package
```

After installing, reference the plugin's schema and theme in `md-sync.yaml`:

```yaml
source: my-resume.md
schema: my-resume          # matches parser.schema
outputs:
  - format: html
    lang: zh
    style: example-style   # matches a name in templates
```

### Packaging

#### 1. Python package (wheel)

```bash
pip install build
python -m build
# artifacts land in dist/md_sync-*.whl, distributable via pip install
```

CLI entry point: `md-sync` (see `[project.scripts]` in `pyproject.toml`).

#### 2. Single-file executables (recommended, no Python required)

The web and desktop editions share the same Dioxus frontend; one command builds both:

```bash
pip install pyinstaller            # or pip install -e ".[build]"

python scripts/build_all.py        # one shot → dist/md-sync-web + dist/md-sync-ui
python scripts/build_all.py --web       # web edition only
python scripts/build_all.py --desktop   # desktop edition only
python scripts/build_all.py --force     # force re-package the backends (skip fingerprint cache)
```

**Artifacts (all under this project's `dist/`):**

| Edition | Artifact path | Notes |
|------|----------|------|
| Web   | `dist/md-sync-web`    | standalone web server; run `./dist/md-sync-web` → open http://127.0.0.1:8580 |
| Desktop | `dist/md-sync-ui`     | Dioxus native window; run directly, embedded backend auto-starts (Unix socket, no network port) |

> A backend fingerprint cache (`dist/.backend-*.fp`) tracks source / dependency / environment changes:
> the bundle is only re-packaged when its inputs changed (e.g. installing `python-docx` triggers a repack
> automatically). `dist/`, `build/`, and `*.spec` are all in `.gitignore` and never committed.
> `dist/md-sync` is the intermediate backend embedded in the desktop binary — handled by the scripts, no manual steps.

- The scripts bundle resources such as `md_sync/templates`, `md_sync/plugins`, and `md_sync/web/static` into the binary, resolved at runtime through `md_sync.template.manager._find_install_dir()` — **nothing needs to be installed on the user's machine**.
- **Use Python 3.12 for building** (PyInstaller's officially supported release). On 3.14, `mypy` must be excluded (the script does `--exclude-module mypy` by default).

#### 3. Cross-platform automated builds (GitHub Actions)

`.github/workflows/build.yml` runs `python scripts/build_web.py` on `ubuntu-latest` / `windows-latest` / `macos-latest` runners and uploads the three-platform Web executables as Release artifacts.

```bash
# tag to trigger the automated build and publish a Release
git tag v1.0.0 && git push origin v1.0.0
# download from GitHub Releases: md-sync-web-linux / md-sync-web-windows.exe / md-sync-web-macos
```

To grab the three-platform binaries without publishing a Release, download them from that run's Artifacts page instead;
artifacts are named `md-sync-web-ubuntu-latest` / `md-sync-web-windows-latest` / `md-sync-web-macos-latest`.
